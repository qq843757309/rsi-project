# RSI 数据平台元数据血缘质量与多团队接入规范

版本 v0.1 建议稿　日期 2026年10月3日

本文面向数据平台研发团队、Agent 开发团队和各业务团队数据负责人，作为架构设计和接入实现的共同依据。建议平台从零建设统一元数据目录和接入契约，在现有 OceanBase、Excel 入库链路及 NAS 上补齐版本、来源、权限、血缘与质量管理。其他团队通过适配器接入，共用平台协议，保留各自的业务字段与实验口径。

本文中的“必须”表示拟采用的技术准入要求，尚不代表已经生效的公司制度。字段、状态、错误码和接口是建议设计，不是对现网实现的描述。保留期限、生产 SLA、科学规则阈值和审批岗位由实施项目登记后生效。

## 1 建设起点和术语

目前已有业务数据：Excel 经脚本写入 OceanBase，数据库约有 3000 张独立实验明细表和少量人工挂测总表，PDF、PPT、Word、MD 等文件保存在 NAS。试点约 50 位用户，已有公司 AD、内网大模型和文本 embedding 服务。平台及统一元数据治理从零建设，不能假定已有公司数据目录、血缘平台、规则库、Git 制品服务或统一模型注册服务。

“原始数据”指文件字节及实验记录的原始值。“元数据”指描述数据的身份、结构、来源、版本、权限、处理过程和可信状态。原始数据已经存在，统一元数据需要补建。对象存储保存原件，元数据服务管理原件的含义与关系；这两项均纳入本规范。

| 术语 | 平台定义 | 示例 |
|---|---|---|
| 资产 asset | 可登记和授权的逻辑对象，身份不随路径变化 | 一份实验报告、一张源表、一个知识条目 |
| 资产版本 asset_version | 某次确定的内容或结构状态 | 报告 V2、Schema V3、记录修订 V5 |
| 数据契约 contract | 生产者与平台约定的数据结构、口径和治理规则 | 团队实验填报模板及单位规则 |
| 加工作业 job | 一个定义明确且版本化的处理过程 | Excel 映射脚本、文档解析任务 |
| 运行 run | 作业的一次实际执行 | 某批 Excel 导入、某次查询 |
| 片段 segment | 可回到原件版本的证据单元 | 第 8 页表格、第 3 张幻灯片、音频时间段 |
| Trace 与 Span | Agent 运行的观测标识和子操作 | 一次请求及其 SQL、检索、模型调用 |
| 数据快照 snapshot | 指定范围的可恢复数据状态 | 一次评测使用的实验视图导出 |

数据库表的“版本”需注明版本对象：Schema 版本、记录修订版本、数据快照分别管理。查询时间、结果 hash 或 Trace 本身不构成可恢复的数据快照。

## 2 架构分工和组件位置

建议采用“一套统一目录，业务与 Agent 分域存储”的方式。平台服务统一登记身份、版本、权限与依赖，各物理系统保存适合它们的数据。PPT 第 1 页给出同一架构，相关组件都是拟建或待验证选型。

| 管理内容 | 存储和组件建议 | 维护责任 |
|---|---|---|
| 实验明细和人工总表 | 保留 OceanBase，通过批准视图和业务 API 访问 | 业务负责人确认口径，平台维护接入服务 |
| 统一元数据 | 自建元数据 API，OceanBase 新建目录逻辑表 | 平台团队维护服务，业务团队确认语义 |
| 原始文件和派生文件 | 私有 S3，Ceph RGW 作为 PoC 候选，NAS 受控副本过渡 | 存储运维负责持久化，平台负责版本登记 |
| 文档处理 | Docling 和格式适配器，OCR 与 ASR 按任务验证 | 平台处理服务维护解析器与版本 |
| 全文与向量索引 | OpenSearch 或 Qdrant 等按需求 PoC，作为可重建副本 | 检索服务维护索引，继承源授权 |
| Agent 轨迹与评测详情 | Langfuse 自托管优先 PoC，Phoenix 为替代 | Agent 团队埋点，平台负责治理关联 |
| Agent 记忆 | OceanBase 保存审核条目和来源，索引辅助检索 | Agent 负责人和专家维护确认状态 |
| 代码和 Prompt | 拟建内网 Git，Prompt 可按选型接 Registry | Agent 团队维护，发布服务固定版本 |
| 模型与训练 Checkpoint | 后续私有 S3 和模型目录，MLflow 按需验证 | 模型团队维护训练与发布清单 |

按 Langfuse 官方自托管架构，应用包含 Web 与 Worker，存储依赖包括 PostgreSQL、ClickHouse、Redis 或 Valkey，以及 S3。它们属于工具专用后端，不替代业务 OceanBase。目录保存 external_ref 和业务引用，避免复制产品整套轨迹表。离线部署、SSO 和精细权限受具体版本及许可影响，PoC 需逐项验证。[Langfuse 官方自托管说明](https://langfuse.com/self-hosting)

Ceph RGW 提供对象存储接口，具体生产选型延续 v4 的成本与运维比较。对象标签只保存辅助标识，跨资产检索、质量状态、审批与血缘由统一目录服务承担。[Ceph RGW 官方说明](https://docs.ceph.com/en/latest/radosgw/index.html)

## 3 元数据的组织方式

### 3.1 共用核心和团队扩展

元数据分为平台核心、领域契约和运行证据。平台核心统一资产身份、版本、项目、负责人、源系统、状态和授权。领域契约定义实验字段、单位、精度、枚举、条件、粒度和缺失值语义。运行证据记录处理版本、输入输出、质量结果与引用位置。

团队扩展放在 extensions 命名空间中，例如 extensions.hk_li_metal_v1。扩展必须有独立 Schema、版本和责任人。核心字段不能被扩展覆盖；未知扩展可暂存，但不进入批准查询语义或正式索引。业务新增字段先在团队契约中明确，再评估是否提升为公司共用概念，防止公共模型被某个团队的习惯绑死。

### 3.2 组织和授权模型

使用 team_id 表示接入团队，project_id 表示研发项目，domain_id 表示业务领域。三者不等同。企业用户身份来自 AD；平台为适配器和 Agent 分配 service_principal、producer_id 及凭据范围。生产者只能写入已登记的团队和项目。

平台不能直接信任请求里的 team_id、project_id、owner 或 classification。认证中间件解析身份，授权服务检查项目成员关系、服务账号写入范围、数据密级和用途。每次查询、文件下载、缓存命中、轨迹查看、导出及记忆检索都要执行授权。

跨团队共享通过单独的共享策略显式登记，指定资产范围、允许用途、有效期和授权人。禁止默认把同内容 hash 的不同团队资产合并成一个可见资产。底层字节去重只能在受控存储层实施，不能改变逻辑身份和权限。

## 4 标识和版本规范

资产 ID 使用平台生成的稳定不透明 ID，推荐 UUID。团队自行提交的外部编号登记为 source_system_id 和 source_key，平台通过两者联合映射资产身份。文件路径、表名、原始行号、S3 Key 和内容 hash 都不能单独作为全局资产 ID。

| 标识 | 作用 | 约束 |
|---|---|---|
| asset_id | 逻辑资产身份 | 全平台唯一，移动路径不变 |
| asset_version_id | 一次确定的资产状态 | 修订新建，旧版本保留引用 |
| record_id 和 revision_id | 业务记录及其修订 | 不依赖 Excel 行号，保留 source_locator |
| contract_id 和 contract_version | 数据契约 | 发布后不可原地修改 |
| processing_run_id | 业务加工的一次执行 | 同次生命周期事件共用 ID |
| agent_id 和 agent_run_id | Agent 定义及一次执行 | 产品 Trace ID 保存为外部引用 |
| trace_id 和 span_id | 观测关联 | 保留父 Span，与平台 Run 建映射 |
| candidate_id 和 release_id | 进化候选与发布 | 候选可失败，发布固定全部依赖 |

同一逻辑文件内容变化产生新 asset_version_id。内容相同、来源不同可各有资产身份。asset_version 记录 content_hash、hash_algorithm、byte_size、mime_type、storage_ref、source_locator、created_at 和 schema_version。数据库资产必须分别记录结构指纹与数据版本能力，不给没有快照能力的表伪造 content_hash。

团队契约采用主次修订版本。新增可选字段一般属于兼容变更；字段改名、类型改变、单位口径改变、粒度变化、必填新增或枚举收窄属于潜在破坏性变更。兼容判断需要 Schema 和语义检查共同完成。涉及破坏性变更时，新旧契约并行登记，适配器显式声明写入版本，消费者逐步迁移。

## 5 业务侧元数据模型

下表为逻辑实体。所有实体默认包含团队、项目、创建者、创建时间和状态；具体物理表可按负载合并或拆分，但 API 语义保持稳定。

| 实体 | 关键字段 | 设计用途 |
|---|---|---|
| source_system | 类型、地址引用、负责人、访问身份、扫描计划 | 管理 NAS、数据库、填报系统等来源 |
| data_contract | Schema、契约版本、领域、规则集、生命周期 | 约束每类接入数据 |
| asset | 类型、名称、归属、负责人、密级、业务描述 | 统一查找和授权 |
| asset_version | 版本、原件引用、hash、父版本、结构版本 | 保存确定状态 |
| schema_field | 字段 ID、名称、类型、单位、含义、空值语义 | 表目录和自然语言 SQL 基础 |
| source_mapping | 源字段、目标字段、转换、映射版本、确认人 | 保留 Excel 和团队字段映射 |
| observation | 记录 ID、实验、批次、电芯、记录修订、测量条件 | 统一定位实验事实 |
| segment | 原件版本、页码、幻灯片、单元格、bbox、时间段 | 回到原始证据 |
| processing_run | 作业版本、输入输出、状态、错误、执行身份 | 加工与质量追溯 |
| index_manifest | 输入版本、切分器、模型、维度、索引位置 | 索引重建和撤回 |
| quality_result | 规则版本、目标版本、结果、严重性、证据 | 发布门禁和修复 |
| policy_binding | 策略 ID、版本、范围和状态 | 按项目执行授权 |

对实验记录保存 raw_value 与 normalized_value，并登记 raw_unit、canonical_unit、conversion_rule_version、method、conditions、precision 和 missing_reason。转换必须保留原值。空字符串、未知、未测量、低于检测限、解析失败各用明确原因表达，不统一填成 0。

### 5.1 三千张表的目录建设

先用只读元数据账号采集表、字段、类型、索引和结构指纹，形成技术目录。再按业务用途和结构特征分为表族，确认项目、电芯、批次、实验等标识以及业务粒度。结构相似只作为分组候选，不能自动认定同一业务口径。

表族契约给出批准字段、单位、有效条件、允许关联、查询视图和示例问题。Agent 查询先根据授权目录检索候选表族，再使用批准语义生成 SQL。禁止一次性把全部三千张表的 DDL 放入上下文，也不能用表名相似直接生成 JOIN。

某些旧表缺少主键时，先登记来源定位及采集批次，在受管副本中分配稳定记录 ID。源表行顺序不能作为持久身份；不能确认同一记录的修订时，保存新采集版本并标记关联未确认。

### 5.2 挂测总表

总表保留人工填报事实，登记 summary_grain、batch_scope、metric_definition、related_detail_refs、entered_by、reviewed_by 和 summary_method。批次汇总与单电芯明细分开表达。仅在业务确认算法和覆盖范围后，才登记可验证的汇总计算血缘；其余关系为人工填报或人工确认，不能自动重算覆盖。

## 6 原始文件和多模态管理

NAS 接入时先登记来源系统和允许目录，由服务身份读取。文件稳定读取后生成受控副本，计算 hash，登记版本，再进入解析。NAS 文件仍修改、复制中断或大小持续变化时，标记待稳定，延迟处理或使用源快照。扫描通知用于触发任务，周期性全量对账发现漏事件。

原位引用可用于早期盘点，但无法保证版本可恢复。正式可引用的资产需受控副本或可验证的源版本机制。源文件重命名、移动、删除与内容修改分别登记。原件在正式区禁止业务直接覆盖，通过新版本 API 修订。

对象路径建议为 team/project/asset/version/part；路径只表达物理组织，平台 ID 才是业务身份。raw、derived、media、trace-archive、evaluation、model-artifacts 和 checkpoints 为逻辑分区，是否独立桶按权限与生命周期确定。对象存储中只放内容和轻量标签，详细 Schema 与业务关系在目录中维护。

上传采用申请版本、临时上传、完整性验证、提交登记和发布的流程。数据库与对象存储不共享单一事务，因此目录使用 STAGING、VERIFIED、PUBLISHED 等状态，任务对账清理孤立文件并补偿未完成登记。消费者只能读取已经通过验证并发布的版本。

PDF、PPTX、DOCX、MD 保留原始文件，派生文本、结构化表格和预览文件各有独立版本与输入引用。旧 PPT、DOC 格式若需转换，记录转换器版本和转换文件，引用仍能回到原件。失败解析进入隔离队列，不把空文本当作成功。

图片登记尺寸、格式、方向和采集来源，裁剪图用 bbox 指向父图版本。音频登记格式、采样率、声道、时长和使用授权，转写及分段用 start_ms、end_ms 指向原音频版本。OCR、ASR 和 embedding 产物记录模型与配置版本。不同 embedding 模型空间不直接混用；文本 embedding 可用并不代表已具备图像或音频检索能力。

## 7 业务血缘的实现

血缘以“输入版本、处理运行、输出版本”为核心，同时保存关系类型、证据位置、采集方式与确认状态。区分设计血缘和实际运行血缘：映射配置说明计划如何处理，实际运行说明这次使用了什么。SQL 候选或模型生成的引用不能直接登记为已确认的实际来源。

建议定义 lineage_edge：edge_id、input_ref、output_ref、processing_run_id、relation_type、source_locator、capture_method、verification_status 和 created_at。关系可包括 COPY、PARSE、NORMALIZE、AGGREGATE、RETRIEVE、CITE、DERIVE、EVALUATE、SUPERSEDE。UNKNOWN 作为确认状态，不猜测缺失历史关系。

OpenLineage 的 Dataset、Job、Run 和运行事件模型可作为对外血缘适配协议。平台内部保留自己的稳定资产 ID 和版本引用，通过适配器映射命名空间及 Facets。文档页码、实验条件和 Agent 证据等扩展需另定版本，不声称全部是标准已有字段。[OpenLineage 官方对象模型](https://openlineage.io/docs/spec/object-model/)

### 7.1 各处理环节的采集点

| 处理环节 | 必须登记的输入输出和版本 | 采集方式 |
|---|---|---|
| Excel 入库和填报 | 文件版本、Sheet、源行或单元格、模板、映射版本、记录修订 | 接入服务和写入事务埋点 |
| 文档解析 | 原件版本、解析器、配置、页码、片段和表格 | 任务服务登记 |
| 单位转换和汇总 | 原值、标准值、规则、输入记录集合、聚合粒度 | 转换服务，人工汇总需确认 |
| SQL 执行 | 实际 SQL、批准视图、执行身份、参数、读取范围、结果引用 | 受控 SQL 服务埋点和解析 |
| 检索与摘要 | 实际片段 ID、版本、排名、索引版本、生成结果 | 检索与回答服务登记 |
| 修订撤回 | 旧新版本、原因、影响资产、执行结果 | 版本服务和依赖传播任务 |

字段血缘可由批准映射、实际 SQL 解析和应用埋点组成。动态 SQL、UDF、外部工具或人工总表缺少可靠解析时，保留表级关系并标记字段待确认。查询日志记录的是读取范围或可定位结果，并不要求复制每次查询的全部行级依赖；有严格复现要求时保存结果和数据快照。

### 7.2 可靠事件和恢复

OceanBase 业务写入和平台事件 Outbox 在同一业务事务中提交，后台投递器至少一次发送，消费者按 source 与 event_id 幂等。跨系统文件任务先持久化阶段状态，再执行上传、校验和登记，通过补偿与对账恢复。仅一次成功的网络调用无法证明端到端仅处理一次。

事件记录生产者时间、平台接收时间、运行状态和序号。乱序事件追加保存，由状态机判定有效状态，不让迟到 START 把 COMPLETE 改回运行中。失败事件保留重试次数、错误分类和人工处理责任，进程崩溃后通过心跳超时及对账确认是否需要补发。

## 8 数据质量和发布门禁

质量结果与资产版本、规则版本绑定。建议 quality_rule 记录 rule_id、version、scope、expression_ref、severity、threshold_ref、owner 和 effective_at；quality_result 保存 target_ref、processing_run_id、observed_value、PASS/FAIL/WARN/UNKNOWN、evidence_ref 和 checked_at。未知不是通过。

| 门禁 | 校验重点 | 未通过的处理 |
|---|---|---|
| 接入门禁 | 身份、项目、契约、必填、类型、唯一性、hash、权限 | 拒收或隔离，返回定位错误 |
| 加工门禁 | 单位转换、片段定位、表格和页数、记录关联、输出完整 | 加工失败或待复核，阻止正式索引 |
| 业务复核 | 实验条件、科学异常、总表粒度、经验冲突 | 保留原始事实，交负责人确认 |
| 查询门禁 | 实际执行正确性、权限、证据支持、空结果与口径 | 拒绝越权，显示限制和来源 |
| 进化门禁 | 冻结评测、版本依赖、制品完整性、权限回归 | 候选留档，禁止正式发布 |

硬性错误包括身份不匹配、无写入权限、Schema 不合法、原件完整性失败及缺少发布所需来源。缺少业务单位、实验标识或关联确认时，根据契约定义隔离范围。科学异常用 WARN 或待复核保留，禁止为了通过检查而删除异常测量。

质量作用域包含字段、记录、批次、文档、片段和整个数据集。一个坏行是否阻断整批导入由契约声明，返回有效行数和错误行定位。查询服务在结果中显示质量状态，未经确认的数据不能悄然作为正式结论。

一期规则以服务及 SQL 校验为主。规则数量和运营需求扩大后评估规则引擎；工具不代替业务定义。观察指标包括契约失败率、重复率、关联待确认率、解析样本准确率、源权限传播成功率、索引延迟和分题型答案正确率。阈值与统计窗口放在版本化契约或 SLA 中，不在本文虚构统一科学阈值。

修复采取新版本、重新执行质量规则、更新血缘、传播索引和缓存失效的过程。原始错误及其处理记录保留。撤权应由权威授权服务立即阻断查询和下载，后台再清理副本，不能等索引删除完成才拒绝访问。

## 9 Agent 侧元数据模型

Agent 数据平面既包含观测数据，也包含可治理资产。Langfuse 管理调用与评测详情；平台目录维护 Agent 身份、业务证据、记忆与发布依赖。所有 Agent 通过网关或 SDK 建立认证上下文，不直接使用业务数据库的生产写账号。

| 实体 | 必需字段组 | 用途 |
|---|---|---|
| agent_definition | agent_id、owner、team、allowed_projects、capability、版本 | 登记接入 Agent 和允许工具 |
| agent_run | run_id、agent_id、principal、project、request_id、status、时间 | 一次请求的治理上下文 |
| observation_ref | provider、trace_id、span_id、external_ref、run_id | 链接观测产品详情 |
| tool_execution | tool/version、Schema、实际输入输出引用、状态、错误 | 追溯 SQL 与工具调用 |
| evidence_ref | 资产版本、片段/记录定位、索引版本、读取策略版本 | 将答案关联到业务证据 |
| feedback | feedback_id、run_id、author、纠正依据、类型、状态 | 区分用户反馈和确认经验 |
| memory_item | kind、namespace、来源、适用范围、审核状态、TTL | 管理可使用的记忆 |
| eval_case 和 eval_run | 数据集快照、评分规则、候选、逐题结果 | 稳定比较 Agent 版本 |
| candidate | 父候选、变更理由、代码/Prompt/模型/工具引用 | 管理自进化谱系 |
| release_manifest | 全部固定依赖、批准人、发布时间、回滚版本 | 支持发布与复现 |

运行记录保存可公开的模型输入输出、工具操作及证据引用，不要求采集模型内部思维过程。API 密钥、数据库密码和个人敏感字段应在采集前按规则过滤。大输入输出与多模态附件使用受控对象引用，日志和目录避免重复保存敏感全文。

### 9.1 采集与去重

SDK 为请求产生平台 run_id，并与 Langfuse trace_id 建映射。所有工具操作关联相同 request_id、项目身份和父 Span。采集适配层可使用产品 SDK 或 OTel Collector，具体导出协议、属性映射和版本兼容在 PoC 中验证。OpenTelemetry 负责遥测处理，不能自行提供完整业务血缘。[OpenTelemetry Collector 官方说明](https://opentelemetry.io/docs/collector/)

关键写入、引用、版本发布和授权事件可靠落库。性能观测可以按契约采样，但采样轨迹不能用于证明业务血缘完整。SDK 缓冲、重试与异步回调不能替代平台关键事件 Outbox。平台对 Agent 请求数量、终态数量、Trace 映射数量和证据引用数量周期性对账。

### 9.2 运行记录如何使用

排障从 request_id 找 run_id 和 Trace，检查实际检索片段、SQL、模型版本及失败工具。质量评测从确认反馈提取用例，固定数据快照和评分规则，避免把测试答案放入线上知识检索。经验沉淀从反馈创建记忆候选，保留原始证据及适用条件，再由专家确认。影响分析通过 evidence_ref 找到依赖旧报告或旧实验数据的答案、记忆和候选。

## 10 记忆和状态规范

会话状态、运行经历、领域知识和可执行技能分别管理。状态 Checkpoint 用于中断恢复，权威知识需审核，可执行技能必须关联代码、工具 Schema 和测试。不能将“曾经生成过”自动视为“可在公司复用”。

memory_item 最少包含 memory_id、kind、team/project、source_refs、valid_scope、review_status、confidence_source、created_by、supersedes、expires_at 和 policy_ref。状态建议为 CANDIDATE、CONFIRMED、CONFLICT、EXPIRED、WITHDRAWN。候选在试验区使用；正式回答仅使用符合查询策略的确认条目。

源资产修订、撤回、密级改变或共享授权到期后，记忆服务按依赖检查适用性。内容存在但无证据访问权限时，禁止通过记忆绕过源权限。专家观点冲突时保存不同条目和适用条件，不简单覆盖为单一“真相”。

一期推荐自建审核条目目录和检索引用。未来可接 Mem0 等生成候选，框架输出仍须符合统一来源、权限及审核规则。LangGraph 持久化可管理线程状态，选用其原生后端时保持官方依赖，不能因为 OceanBase 为 MySQL 兼容就假定所有 Checkpointer 可直接使用。

## 11 自进化资产规范

候选是数据资产，发布是状态改变。知识、Prompt、技能和模型候选都登记父候选及变更理由，评测失败的候选保留，正式版本从固定依赖清单构建。

| 资产 | 最小版本信息 | 存储职责 |
|---|---|---|
| 源码和工具技能 | Git Commit、依赖锁、工具 Schema、测试和构建结果 | Git 管源码，制品库管发布包 |
| Prompt | 模板、变量 Schema、版本、模型配置、路由和适用范围 | Git 或选定 Registry 管权威版本 |
| 模型制品 | 基础模型、权重、Tokenizer、Adapter、配置、manifest 与 hash | 私有 S3 管大文件，目录管状态 |
| 训练 Checkpoint | 训练 Run、步数、权重、优化器等恢复状态、数据快照 | 训练热存储与持久归档分开 |
| Agent 状态 Checkpoint | 会话、状态结构版本、节点和恢复依赖 | Checkpointer 管状态，目录管引用 |
| 评测资产 | 冻结数据集、评分规则、逐题结果、候选版本 | S3 管大文件，评测服务管运行 |

release_manifest 固定 code_commit、prompt_version、tool_versions、model_digest、dataset_snapshot_refs、index_manifest_refs、policy_version、eval_run_refs 和 rollback_release_id。在线数据依赖持续变化时，发布记录同时说明可复現范围，不能承诺仅凭清单完全重现历史答案。

模型进化启动后才引入训练注册与恢复流程，一期先完成依赖登记。没有训练快照、实验结果可恢复版本和确定性配置时，报告必须明确复现限制。

## 12 多团队数据标准

### 12.1 平台核心标准

所有接入统一 UTF-8 JSON、稳定 ID、UTC 时间及明确业务时区，数值类型与精度、单位代码、空值语义和错误码遵循契约。时间保存事件发生与平台接收两个时间，原时区可保留，避免把设备时间当作可靠全局顺序。

Schema 用 JSON Schema Draft 2020-12 描述结构。类型检查之外的权限、引用存在性、跨字段语义、单位转换和生命周期由业务校验器完成。format 是否严格验证取决于验证器配置，需要显式开启日期、URI 等检查。[JSON Schema 官方验证规范](https://json-schema.org/draft/2020-12/json-schema-validation)

统一错误响应包含 code、message、request_id、contract_version、field_path、source_locator、severity、retryable 和 evidence_ref。错误不暴露无权限项目或原件详情。建议错误码包括 CONTRACT_INVALID、SCOPE_DENIED、SOURCE_UNSTABLE、HASH_MISMATCH、REFERENCE_MISSING、VERSION_CONFLICT、QUALITY_BLOCKED 和 PAYLOAD_CONFLICT。

### 12.2 团队领域契约

每个团队定义字段语义、实验粒度、标识来源、单位、方法、条件、枚举、范围、缺失原因及修订方式。字段别名映射到稳定 field_id，而非强迫所有团队改用同一 Excel 列名。单位转换必须有规则版本和适用范围，语义不同的测量即使单位相同也不能自动合并。

例如团队 A 的“循环次数”和团队 B 的“cycle_no”可以在含义和起算方式一致后映射到同一概念；若统计区间不同，保留各自字段并登记差异。实验表的一行究竟代表电芯、测量点还是批次，必须明确为 grain。自然语言查询按 grain 和批准关联处理结果。

### 12.3 Agent 和工具契约

Agent 接入声明 agent_id、负责人、调用项目、允许工具、输入输出 Schema、SDK 版本、事件协议、模型服务引用、Prompt 与工具版本策略。工具登记只读或写入能力、输入 Schema、超时和错误语义。新增写入工具必须通过权限、幂等、失败恢复与人工授权策略验证，不能沿用只读工具的准入结论。

接入对象不局限于同一 Agent 框架。平台提供 HTTP API、事件协议和轻量 SDK，团队可用 LangChain、LangGraph 或自研框架实现适配。平台 API 管身份与契约，观测产品接收轨迹。更换 Agent 框架不改变资产 ID 和业务权限语义。

| 类别 | 所需登记 | 是否属于生产前必需 |
|---|---|---|
| 团队归属 | team、project、domain、业务与技术负责人 | 是 |
| 身份和权限 | producer_id、服务身份、AD 映射、写入与读取范围 | 是 |

| 语义 | 字段、单位、方法、缺失值、枚举、映射版本 | 结构化业务数据必需 |
| 文件 | 格式、大小约束、hash、定位、版本与恢复机制 | 文件数据必需 |
| 质量 | 硬性规则、科学复核、失败粒度、负责人 | 是 |

## 14 准入流程和验收

1. 登记团队、项目与生产者。绑定身份和权限，明确责任人。
2. 提交契约、映射、代表性数据和版本策略。平台验证结构，业务负责人确认语义。
3. 在隔离沙箱接入。验证成功、失败、重复、乱序、断网、撤权、修订和恢复场景。
4. 平台登记准入结果、测试证据和允许能力。生产凭据限制到已经通过的项目、契约和接口。
5. 上线后监控数据漂移、失败率和事件对账。破坏性变更重新准入，旧版本按迁移计划退役。

| 验收场景 | 判定要求 | 证据 |
|---|---|---|
| 正常接入 | 产生资产版本、来源、质量结果和终态事件 | 目录记录及可下载原件 |
| 相同幂等键重复提交 | 相同内容返回原受理结果，不重复产生业务记录 | 请求与写入计数 |
| 相同幂等键不同内容 | 拒绝并返回 PAYLOAD_CONFLICT | 比较 hash 和错误记录 |
| 越权项目或团队 | 写入、读取、检索、导出和下载都拒绝 | 授权审计与拒绝响应 |
| 原件被覆盖或重命名 | 已引用版本仍可恢复，新内容生成新版本 | 新旧版本和原件 hash |
| 解析或单位映射失败 | 阻止失败资产正式发布，返回证据位置 | 隔离状态与质量结果 |
| 任务中断和事件乱序 | 可对账恢复，状态不倒退 | Outbox、重试与运行终态 |
| Schema 破坏性变更 | 未通过准入版本不进入生产语义 | 契约版本与拒绝记录 |
| Agent 答案追溯 | 能找到实际 SQL 或检索证据的资产版本 | Run、Trace 和 evidence_ref |
| 修订和撤权 | 旧索引、缓存和记忆不能继续泄漏，依赖能定位 | 失效任务和授权回归 |
| 跨团队独立适配 | 同名源字段不会串项目，扩展不覆盖平台核心 | 两团队样例及隔离测试 |
| 候选发布与回滚 | 固定依赖版本，评测失败不发布，已发布可回滚 | 评测证据和 manifest |

以上硬性准入项目要求测试中全部通过。吞吐、时延、容量和科学准确性阈值依据真实样本及负责人登记的 SLA 设定，不把 50 位注册用户等同于 50 个并发查询。

## 15 接口与事件规范

建议提供以下 API，具体路由可调整，语义保持一致：

| 接口 | 核心语义 |
|---|---|
| POST /v1/contracts | 登记契约草稿，校验和审批后发布 |
| POST /v1/assets | 申请稳定资产身份和项目归属 |
| POST /v1/assets/{id}/versions | 申请版本，返回受控上传方案 |
| POST /v1/versions/{id}/commit | 校验完整性与契约后完成版本登记 |
| POST /v1/ingestions | 受理填报或批量导入，返回任务和逐条结果 |
| POST /v1/events | 幂等接收运行、质量和血缘事件 |
| POST /v1/agent-runs | 登记请求上下文并返回平台 Run ID |
| POST /v1/feedback | 登记反馈及证据，创建待审核候选 |
| GET /v1/assets/{id}/lineage | 返回已授权的依赖，隐藏无权节点细节 |
| POST /v1/versions/{id}/withdraw | 登记撤回并触发依赖失效 |

接入 API 的幂等键作用域为身份、接口和项目；同键同内容重复提交返回原结果，同键不同内容冲突拒绝。修订使用 expected_version 或等价乐观锁，不以最后一次写入直接覆盖。

事件信封建议采用 CloudEvents 1.0 的结构，内部事件增加 dataschema 和 payload_version，保留 source、id、type、time 与 subject。幂等依据 source 与 id 的组合，不能仅用 Trace ID。它规定事件表达方式，不提供鉴权、消息队列或事务一致性。[CloudEvents 官方规范](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)

配套规范模板目录提供 asset.schema.json、event.schema.json 和 data-contract.schema.json，以及两个可验证示例。内网上线时将 Schema 复制到内部注册服务，外部规范 URI 只作标识；运行时使用本地 Schema 注册表，不请求互联网。JSON Schema 校验不承担跨实体引用或访问授权。

## 16 使用实例

一批实验明细由 Excel 导入。接入服务从登录身份确定团队和项目，验证契约，保存原 Excel 版本，将 Sheet 和源行映射到记录 ID。入库时提交记录修订、质量结果和 Outbox，目录建立文件版本到入库 Run、再到记录修订的血缘。

实验员随后在挂测总表填写批次汇总。平台保存人工填报人、口径及覆盖批次，与相关明细建立人工确认关系，不覆盖原有明细。某报告引用总表数据时，业务确认关联或处理任务登记引用，不能只通过文字相似推定精确来源。

专家向 Agent 查询一批电芯的实验结果及报告依据。查询服务先按项目授权取得表族与文档候选，执行实际 SQL 和检索，在回答中返回结果粒度、质量状态和证据位置。SDK 记录 Trace，目录登记 Agent Run 与业务 evidence_ref。专家纠正某个口径后，平台保存反馈并创建待审核记忆，确认和评测通过后纳入下一发布版本。

另一团队使用不同 Excel 列名和单位，只需提交自己的数据契约和映射适配器。平台共用资产、版本、事件与授权协议，其私有字段保存在命名空间扩展。跨团队查询仅在共享策略覆盖的数据范围内生效。

## 17 从零建设的实施顺序

### 17.1 基础目录

建立团队、项目、来源、契约、资产和版本服务。采集存量表结构和 NAS 文件清单，进行负责人确认和表族分组。历史仅有当前文件或当前表状态时，登记为首次观察状态，observed_at 为采集时间；已知文件时间另外保存，未知来源标 UNKNOWN。禁止补造历史入库 Run、专家确认或过去的精确血缘。

### 17.2 可靠接入与治理

在现有脚本外增加适配层，先纳管代表性表族与文件类型。建立受控原件、Outbox、加工 Run、血缘、质量隔离和撤权传播。构建元数据 API 和后台人工问题处理入口，解决“谁维护”和“谁确认”的责任归属。

### 17.3 查询与 Agent 数据平面

建立批准语义和查询工具、受权检索及证据引用。完成 Langfuse 和 Phoenix 的内网 PoC，优先选择一个主观测平台。实现 Trace 与业务 Run 的映射、反馈与记忆审核、评测快照和版本清单。正式组件以真实部署验证为准。

### 17.4 扩展团队及后续进化

用第二个团队验证标准与适配边界，完成准入模板及变更管理。代码和模型进化阶段再增制品注册、沙箱、训练数据快照和恢复状态。公司级目录规模或连接器需求扩大时，可以评估 OpenMetadata 等目录平台；统一协议与稳定 ID 允许迁移，自建目录不是永久锁定物理实现。

## 18 维护责任和设计验收

平台团队负责稳定 ID、契约注册、元数据 API、状态机、血缘、质量执行、授权及对账。业务数据负责人负责字段含义、粒度、单位、实验标识、科学阈值、总表口径和共享用途。Agent 团队负责 SDK、工具 Schema、Prompt 和模型引用、运行终态及候选清单。专家负责经验适用条件与评测答案确认。存储和服务运维负责备份、恢复、容量、离线升级及故障处理。

当前设计的最小完成条件是：一份正式资产能找到归属和来源，确定所用版本，回到原始证据，看到质量与授权状态，查出加工和使用依赖；一个新团队能凭契约和适配器完成接入；一次 Agent 发布能说明所用代码、Prompt、工具、模型、索引和评测版本。上述能力落实为数据结构、接口和准入证据后，才算元数据管理进入平台，而非只在架构图中新增一个框。

# RSI 数据平台元数据与血缘具体实现说明

版本 v1.0 讨论稿　日期 2026年10月3日

本文回答三个实现问题：元数据具体存在什么表里，各业务模块什么时候读写这些表，以及血缘怎样采集、保存和查询。它是上一份准入规范的实现补充，面向平台研发人员和方案评审人员。文中的表名、接口及流程为建议设计，尚未在公司的 OceanBase 环境执行验证。

**建议复用现有 OceanBase 的 MySQL 兼容租户，建立独立的元数据逻辑库或表域，并在应用中实现元数据服务模块。不是只建一张大表，也不需要为了元数据再引入一套 MySQL。** 文件字节继续存受控 NAS 或私有对象存储，实验事实继续存业务表，轨迹详情由 Langfuse 等产品管理。统一元数据目录保存它们的身份、版本、位置、权限和关联。

元数据服务一期可以是现有后端中的一个模块，与入库、文件、查询服务一起部署。API 和写入责任明确后，再按负载拆成独立服务。它不要求一开始就建设复杂微服务系统。

## 1 先看一个实际例子

假设实验员导入一份 Excel，入库到实验明细表，专家随后使用 Agent 查询，并将纠正后的经验保存为记忆。

| 内容 | 数据本身存在哪里 | 元数据记什么 |
|---|---|---|
| 原 Excel | 私有 S3 或受控 NAS 副本 | 文件 ID、版本、hash、路径、项目、上传人 |
| 导入后的实验明细 | OceanBase 业务表 | 表和字段定义、实验粒度、单位、入库批次、来源版本 |
| 导入过程 | 任务状态和错误记录 | 脚本版本、输入文件、输出记录范围、成功或失败 |
| Agent 查询 | 业务 SQL 结果和返回答案 | 使用哪个项目、哪些表/片段、哪个 Prompt 和模型版本 |
| Agent 轨迹 | Langfuse 专用后端 | 平台 Run 对应哪个 Trace，业务证据引用是什么 |
| 确认后的记忆 | 记忆内容表或受控内容存储 | 记忆版本、来源、专家确认、适用范围、失效状态 |

业务记录里的“容量是多少”是业务数据。字段“容量”的单位、含义和来源是元数据。某条记忆的正文是知识内容，而“它来自哪次查询、哪份报告、谁确认、适用于什么条件”是记忆元数据。

## 2 各模块如何连接

```text
Excel 入库服务 ─┐
实验填报服务 ──┤
NAS 文件接入 ──┤      元数据服务模块            元数据逻辑库
解析与索引任务 ┼────→ 登记 / 查询 / 修订 ─────→ OceanBase meta_* 表
查询与 Agent ──┤      身份与权限校验              资产 / 版本 / 字段
轨迹适配器 ────┤      事件受理与血缘投影          Run / 输入输出 / 血缘
记忆审核服务 ──┘      依赖查询与失效传播          Agent / 证据 / 记忆

各业务模块分别访问自己的物理数据存储：
实验业务表、NAS 或 S3、全文/向量索引、Langfuse 后端。
元数据服务通过 ID 和版本引用连接这些存储中的对象。
```

元数据服务不搬运所有数据，不代理每一次大文件字节传输。它为文件服务提供受控位置和访问策略，为查询服务提供表目录和证据，为记忆服务提供来源与有效性。文件下载仍经授权的资产接口，Agent 不直接拿目录中的 URI 绕过权限下载。

| 模块 | 向元数据服务写入什么 | 从元数据服务读取什么 | 交互时机 |
|---|---|---|---|
| 结构化入库和填报 | 原件/提交版本、入库 Run、映射版本、输出范围 | 表族契约、字段、单位、项目权限 | 入库前校验，提交后登记完成 |
| 非结构化文件接入 | 文件身份、内容版本、位置、hash | 来源登记、项目、已有版本、存储规则 | 上传或扫描时、原件提交时 |
| 解析和 OCR/ASR | 加工 Run、片段位置、派生文件、处理版本 | 已发布原件及解析配置 | 每次解析、重试和重处理 |
| 全文和向量索引 | 索引 manifest、输入版本、模型与维度 | 获准片段和源权限 | 索引构建、更新、撤回 |
| 查询服务 | 实际 SQL/检索引用、结果引用、运行状态 | 授权表族、字段语义、允许关联、证据 | 查询前取目录，执行后写证据 |
| Agent SDK 和轨迹适配 | Agent Run、Trace 映射、版本和公开调用引用 | 可用工具、项目范围、运行清单 | 请求开始、子调用、请求终态 |
| 记忆服务 | 记忆版本、来源、审核状态、适用范围 | 来源有效性、授权、依赖影响 | 创建、审核、使用、失效 |
| 质量服务 | 规则版本、检测结果、失败位置 | 目标版本、契约和规则 | 接入、加工及发布门禁 |
| 治理管理页面 | 业务含义、负责人确认、修订原因 | 目录、血缘、待确认问题 | 人工维护和变更审核 |

各模块调用统一接口或应用内部方法，避免每个团队直接修改目录表。查询权限和字段定义可缓存，但使用时仍校验有效策略，撤权不能等待缓存自然过期。

## 3 需要建哪些表

建议先实现下面 8 张共用核心表，再增加 4 张 Agent 扩展表。数量是为了说明最小实现的分工，后续可依据查询负载调整，不能把这个数理解成完整平台只能有 12 张表。

### 3.1 八张共用核心表

| 表名 | 一行代表什么 | 关键字段 |
|---|---|---|
| meta_source | 一个来源系统 | source_id、类型、地址引用、负责人 |
| meta_asset | 一个逻辑资产 | asset_id、类型、团队、项目、名称、当前版本、策略 |
| meta_asset_version | 一个确定的资产版本 | version_id、asset_id、版本类型、原件引用、hash、状态 |
| meta_field | 某个结构版本下的一个字段 | field_id、version_id、字段名、类型、单位、含义、粒度 |
| meta_processing_run | 一次导入、解析、索引或工具处理 | run_id、job/version、状态、输入参数引用、错误 |
| meta_run_io | 一次处理的一个输入或输出 | run_id、方向、asset_version_id、定位范围 |
| meta_lineage_edge | 一条可查询的血缘关系 | 输入版本、输出版本、run_id、关系、确认状态 |
| meta_outbox | 一条待投递的可靠事件 | event_id、source、payload、投递状态、重试次数 |

meta_asset 保存逻辑身份，meta_asset_version 保存历史内容版本。路径变化可更新定位映射，内容变化创建新版本。meta_processing_run 记录“发生了哪次处理”，meta_run_io 记录“这次具体读写了什么”。meta_lineage_edge 是由这些输入输出生成的查询关系。

**元数据不需要为现有 3000 张业务表各建一张目录表。** 所有业务表共用 meta_asset 和 meta_field。例如 3000 张表对应约 3000 条表资产登记，字段对应更多 meta_field 记录，再通过表族和业务语义管理。

### 3.2 四张 Agent 扩展表

| 表名 | 一行代表什么 | 关键字段 |
|---|---|---|
| meta_agent_run | 一次 Agent 请求 | agent_run_id、agent/version、用户、项目、Prompt/模型/工具版本 |
| meta_trace_ref | 一个产品观测标识的映射 | agent_run_id、provider、trace_id、span_id、external_ref |
| meta_evidence_ref | 一次调用使用的一项业务证据 | agent_run_id、processing_run_id、资产版本、定位、读取时间 |
| meta_memory_item | 一个记忆内容版本的治理状态 | asset_version_id、记忆种类、内容引用、审核人、适用范围 |

质量规则、质量结果、权限策略和数据契约另有治理表或服务。本文附带的 SQL 仅展示上述 12 张表，不包含完整规则引擎和权限系统。目录保存它们的引用，实际权限不能只靠一个 policy_ref 字符串完成。

### 3.3 一张资产表会是什么样

下面使用短编号方便阅读，生产建议使用稳定 UUID。这些是虚构示例。

| asset_id | 类型 | 名称 | 当前版本 | 说明 |
|---|---|---|---|---|
| A01 | FILE | 批次实验明细.xlsx | V01 | 原 Excel 文件 |
| A02 | TABLE | 实验明细表 | V02 | 业务表目录，V02 是结构版本 |
| A03 | DATASET | 本次导入的实验记录范围 | V03 | 指向入库批次/记录修订 |
| A04 | FILE | 实验报告.pdf | V04 | 报告原件 |
| A05 | SEGMENT | 报告第8页表格 | V05 | 文档片段及定位 |
| A06 | RESULT | 一次查询的保存结果 | V06 | 确需复现时保存的结果 |
| A07 | MEMORY | 专家确认的经验 | V07 | 知识内容版本 |

没有保存查询结果时，不要求每次请求都产生 RESULT 资产，仍保存 Run 和实际读取证据。数据血缘可以追溯读写关系，是否能重放原答案由源数据版本和结果保存能力决定。

## 4 结构化数据入库如何交互

### 4.1 先纳管已有三千张表

只读目录采集器读取表名、字段类型、索引等技术结构，为每张表登记 meta_asset，为结构变化登记 meta_asset_version，并写入 meta_field。MySQL 的 INFORMATION_SCHEMA.COLUMNS 可以提供列信息；OceanBase 现网支持情况和字段差异需要用实际版本验证。[MySQL 官方列目录说明](https://dev.mysql.com/doc/refman/8.4/en/information-schema-columns-table.html)

系统采集不到字段的业务含义、实验粒度、单位和允许 JOIN 的关系。业务负责人在治理页面补充这些信息，平台形成批准表族。现有脚本历史未记录来源时，首次登记为当前观察状态，历史来源标记未确认，不能补造旧血缘。

### 4.2 Excel 导入的一次完整流程

1. 入库服务根据身份确认项目，向元数据服务获取契约、目标表、字段映射、单位和允许写入范围。
2. 文件服务保存 Excel 受控原件，登记文件资产和版本，记录 hash、Sheet 等来源位置。
3. 入库服务创建 meta_processing_run，job_version 对应这次使用的脚本和映射配置。输入 meta_run_io 指向 Excel 版本。
4. 服务执行校验，在业务表写入实验记录，为记录保留稳定 ID、修订号或至少 ingest_batch_id。科学异常不自动删除，按规则交复核。
5. 与业务写入一同提交源端 Outbox 事件，事件包含原 Excel 版本、入库批次、记录范围、脚本版本和质量结果引用。
6. 事件消费者更新 Run 终态，登记输出范围资产 V03，写入 meta_run_io，并生成 V01 经 Run R01 到 V03 的血缘关系。
7. 达到发布门禁后，目录将输出标记为可用。查询服务使用已发布视图，能够回到原 Excel 和源行位置。

```text
Excel 原件版本 V01
        │ INPUT
        ▼
导入 Run R01  脚本 commit + 映射版本
        │ OUTPUT
        ▼
记录范围版本 V03  ingest_batch_id + record_id/revision_id
        │ 所在业务表
        ▼
OceanBase 实验明细
```

入库应区分三个层次：表 Schema 的版本、此次写入的记录范围、可恢复的数据版本。记录集合 V03 只有保存修订历史或导出快照时，才具有精确恢复能力。只保存 ingest_batch_id 和主键范围时，需要说明它是定位范围，未来原行覆盖后无法保证原值重现。

### 4.3 为什么不能简单先写业务表再调用元数据 API

业务库写入成功后，远程元数据 API 可能失败，产生“数据已入库但没有来源”的缺口。因此原子性由源端保证：业务写入和 Outbox 在同一个实际事务中提交，目录异步消费。最终目录可能短暂滞后，但事件不会因为进程退出而丢失。

如果所有模块都在同一个应用和可验证的数据库事务范围内，也可以直接一起写目录和业务表。跨服务 API 调用不属于本地事务；不同租户或不同数据库实例不能假定具有同一事务。具体事务范围需在 OceanBase 环境验证，无法共事务时采用源端持久化事件与对账。

实验填报页面采用同一流程，来源是一次提交版本而不是 Excel 文件。人工挂测总表记录填报人、批次覆盖和口径，建立人工确认的关联，不默认由所有明细自动汇总生成。

## 5 非结构化文件如何交互

文件的实际字节存 NAS 或 S3；元数据表只保存文件的位置、版本与处理结果引用。PDF 不以 BLOB 形式塞入 meta_asset。

| 步骤 | 文件或任务动作 | 元数据动作 |
|---|---|---|
| 登记 | 扫描 NAS 或接收上传 | 获取归属，申请 asset_id 和待提交 version_id |
| 保存 | 上传临时对象或保存受控副本 | 版本保持 STAGING，不供检索使用 |
| 校验 | 确认文件稳定、大小和 hash | 完整性通过后改为 VERIFIED |
| 解析 | 解析文字、表格、图片或转写 | 创建 Run，登记原件输入与派生输出 |
| 定位 | 生成文档片段和表格 | 每个片段引用父原件版本与页码/坐标 |
| 索引 | 构建全文或向量索引 | 登记索引版本、输入片段和模型配置 |
| 发布 | 校验权限、质量和证据 | 发布版本，通知查询服务可用 |

片段一般作为独立资产或片段域记录管理。meta_asset_version 的 locator_json 保存页码、Sheet/单元格、bbox 或音频时间段；parent_version_id 保存父原件版本。片段数量较大时，正文存专用片段表或对象文件，目录保存引用。源权限变化必须传播到这些派生对象。

解析结果的例子：原件 V04 经解析 Run R02 产生 V05，V05 的定位为 page=8、table=2，并记录 parser_version。索引 Run R03 读取 V05，输出索引 manifest，登记 embedding 模型、维度和索引位置。重解析时创建新 Run 和新片段版本，不覆盖旧版本。

对象存储和目录不具备共同事务。实现时先保存原件、校验、提交版本；目录状态控制可见性。对账任务处理“有对象没有登记”和“目录仍在 STAGING”的情况，重试同一提交需幂等。原 NAS 文件覆盖时，已有受控副本仍可恢复。

## 6 Agent 轨迹如何交互

**轨迹也有元数据，但统一目录没有必要复制每个 Token、每段全文和产品所有 Span。** Langfuse 管观测详情，平台目录管业务身份与证据关联。

按官方自托管架构，Langfuse 有自己的 PostgreSQL、ClickHouse、Redis/Valkey 和 S3 依赖。平台不直接修改这些产品内部表，也不把它们强制替换成业务 OceanBase。通过 SDK/API 和 trace_id 映射实现连接。[Langfuse 官方自托管说明](https://langfuse.com/self-hosting)

### 6.1 一次查询的流程

1. 网关从 AD 或服务身份确定用户、项目和用途，创建 meta_agent_run。固定本次 Agent、Prompt、工具和模型的版本引用。
2. SDK 创建产品 Trace，将平台 agent_run_id 作为关联属性，meta_trace_ref 保存映射。不能让客户端任意声明其项目授权。
3. 查询服务读取元数据目录，取得授权表族、字段语义和允许关联；文档检索读取已获准片段。
4. SQL 或检索工具创建 meta_processing_run，作为 Agent 的子处理。实际执行成功后，登记读取范围及 meta_evidence_ref。
5. LLM 生成答案，保存实际引用位置和结果引用。轨迹详情异步写观测平台，关键证据事件可靠落库。
6. 更新 Agent Run 为成功、失败或取消。回答接口返回可授权查看的来源，专家反馈与该 Run 关联。

例如 meta_agent_run 保存 Q01，meta_trace_ref 保存 Q01 对应 Langfuse Trace T01，meta_evidence_ref 保存 Q01 使用了报告片段 V05，以及某张表的结构版本和实际读取记录范围。查询失败也保存终态及错误引用。

当 Trace 投递延迟时，meta_agent_run 和证据仍能通过平台查到，后台补齐 external_ref。不能把“观测平台暂时没有 Trace”当作业务请求没有发生。反过来，有 Trace 也不表示业务血缘完整，必须有实际输入输出与证据引用。

### 6.2 哪些信息不采集

保存公开模型输入输出、实际工具操作和版本引用，不要求记录模型内部思维过程。凭据和敏感字段在采集前过滤；大输入输出通过受控存储引用，全文保留规则按项目确定。观测可采样，关键写入和证据事件不能用采样替代完整登记。

## 7 Agent 记忆如何交互

记忆需要有两个部分：内容和治理信息。短文本可存在记忆内容表，长内容和附件存在 S3；向量索引用于检索，不能作为唯一的权威记忆库。

| 记忆信息 | 保存位置 | 说明 |
|---|---|---|
| 正文或附件 | 内容表或 S3 | memory_content_ref 指向固定内容版本 |
| 资产和版本 | meta_asset / meta_asset_version | 与文件采用相同身份和版本规则 |
| 记忆类型、审核、条件 | meta_memory_item | 候选、确认、冲突、失效等状态 |
| 来源关系 | Run 输入输出与 lineage_edge | 指向原报告、查询结果、反馈等版本 |
| embedding | 向量索引 | 携带 memory_version_id，服从有效性和权限 |

专家纠正 Q01 后，记忆服务创建候选资产 A07/V07，来源为实际证据、反馈及 Q01。专家确认适用范围和内容，meta_memory_item 更新为 CONFIRMED。只有状态、权限和来源有效性都满足规则的记忆才进入正式调用。

记忆修订创建新内容版本，旧版本保留，当前版本指针更新。审核状态可以按状态机变化，已登记的历史内容不能静默改写。Langfuse 不是自动成为权威记忆库，平台仍需记忆目录和审核接口。

Agent 使用记忆前，由记忆服务检查元数据：当前版本、适用项目、有效期、审核状态、源权限及来源撤回状态，再进行检索或返回内容。不能让向量库召回一条过期经验后直接交给模型。

源报告撤回时，血缘找到依赖该报告的记忆，失效或待复核。授权服务先阻断访问，后台再更新向量和缓存。源数据修订不必把所有历史运行删除，应保留审计记录，但历史内容的展示仍受当前权限与保留规则约束。

## 8 血缘具体存什么

元数据描述对象。血缘描述对象之间的生成、使用和修订关系。建议血缘也存 OceanBase 关系表，暂时无需引入图数据库。

### 8.1 Run 和输入输出表是事实来源

meta_processing_run 的一行记录这次任务的代码/配置版本和状态。meta_run_io 的多行记录它的输入和输出。例如：

| run_id | direction | asset_version_id | 定位或范围 |
|---|---|---|---|
| R01 | INPUT | V01 | Excel Sheet1 第2至101行 |
| R01 | OUTPUT | V03 | 入库批次 B01，指定记录修订集合 |
| R02 | INPUT | V04 | PDF 原件 |
| R02 | OUTPUT | V05 | PDF 第8页表格 |
| R04 | INPUT | V03 | SQL 实际读取记录范围 |
| R04 | INPUT | V05 | 检索实际返回片段 |
| R04 | OUTPUT | V06 | 保存的查询结果 |
| R05 | INPUT | V06 | 查询结果和专家反馈 |
| R05 | INPUT | V05 | 记忆支持证据 |
| R05 | OUTPUT | V07 | 待审核的记忆版本 |

元数据服务在 Run 完成时，根据实际映射生成 meta_lineage_edge，用于快速上游追溯和下游影响分析。输入输出多时，不能简单把所有输入和输出做笛卡尔积，否则会虚构每个字段都依赖全部输入。无法确定精细映射时，返回 Run 层依赖并标记粒度。

### 8.2 血缘边表

| input_version_id | output_version_id | run_id | relation_type | verification_status |
|---|---|---|---|---|
| V01 | V03 | R01 | IMPORT | OBSERVED |
| V04 | V05 | R02 | PARSE | OBSERVED |
| V03 | V06 | R04 | QUERY_READ | OBSERVED |
| V05 | V06 | R04 | RETRIEVE | OBSERVED |
| V06 | V07 | R05 | DERIVE_MEMORY | OBSERVED |
| V05 | V07 | R05 | SUPPORT | CONFIRMED |

OBSERVED 表示服务看到了实际执行，CONFIRMED 表示相关语义已经确认，UNKNOWN 表示没有可靠关系。实际使用了某份资料，不等于专家认可其科学正确性；科学确认另由审核和质量状态表示。

源字段和目标字段可作为血缘边的补充字段，记录 field_id 与映射版本。一期先覆盖表级、文件/片段级和处理 Run 级，再逐步完善重要字段及记录范围。普通表读取事件可能只引用 TABLE_SCHEMA 版本和查询范围，这种关系说明访问对象，不构成数据值快照。

OpenLineage 的 Dataset、Job、Run 与运行事件模型可作为外部适配基础。平台内部血缘仍用自己的资产版本 ID，适配器负责映射。协议不会自动替平台采集 Excel 脚本、人工总表或记忆审核的来源。[OpenLineage 官方模型](https://openlineage.io/docs/spec/object-model/)

## 9 血缘如何被查询和使用

### 9.1 查看某项记忆的上游

服务先确认用户有权读取 V07，然后查询 output_version_id=V07 的边，得到 V06 和 V05，再向上展开。每一层返回节点前都做授权；无权限来源不展示文件名、内容或数量等可能泄露的信息。

### 9.2 分析某份报告的下游

报告 V04 修订或撤回时，查询 input_version_id=V04 的边，找到 V05；继续找到索引、查询结果和记忆。失效传播任务按资产类型执行重解析、索引重建、缓存清理或记忆复核。资产与 Run 的历史关系保留，另外登记撤回原因和执行结果。

### 9.3 SQL 的查询方式

```sql
-- 查一跳下游。使用绑定参数，由服务先后执行授权。
SELECT output_version_id, run_id, relation_type, verification_status
FROM meta_lineage_edge
WHERE team_id = :team_id
  AND project_id = :project_id
  AND input_version_id = :version_id;

-- 查一跳上游。
SELECT input_version_id, run_id, relation_type, verification_status
FROM meta_lineage_edge
WHERE team_id = :team_id
  AND project_id = :project_id
  AND output_version_id = :version_id;
```

项目过滤只是示例，跨团队显式共享需要真实授权服务处理，不能仅靠 WHERE project_id 达成完整权限管理。服务可逐层做广度搜索，设置最大深度、最大节点数和已访问集合，避免图循环或超大结果。MySQL 支持递归 CTE，但是否用于现网 OceanBase 需版本验证；一期使用应用遍历即可。[MySQL 官方 CTE 说明](https://dev.mysql.com/doc/refman/8.4/en/with.html)

meta_lineage_edge 给输入和输出分别建组合索引。字段级关系、日志及事件会增长，按真实速率制定归档；可以把旧事件保存到对象存储，保留关系查询需要的目录记录。只有跨公司复杂图查询的成本出现明确瓶颈后，再评估图数据库和专用目录。

## 10 怎样避免漏写和写错元数据

元数据模块需要有可维护的行为规则，而非允许任何调用者自由写表。

| 问题 | 实现办法 |
|---|---|
| 同一数据重复提交 | 身份、项目、接口和幂等键联合去重，同键异内容拒绝 |
| 业务写完但元数据调用失败 | 业务事务提交 Outbox，目录至少一次消费并幂等 |
| S3 上传完但目录失败 | STAGING 状态和对象对账，补提交或清理孤立对象 |
| 事件到达顺序错乱 | 保存事件标识和状态机，不允许迟到 START 覆盖 COMPLETE |
| 结构变更未通知 Agent | Schema 指纹扫描，批准语义版本更新，目录缓存失效 |
| 元数据指向不存在的原件 | 提交时检查，周期对账，缺失版本停用并告警 |
| 旧来源仍进入记忆和索引 | 权威授权与有效性检查先阻断，后台做依赖传播 |
| 3000 张表全部人工维护 | 技术结构自动采集，表族语义由业务负责人确认 |

源事件不可静默覆盖。重投同一事件按 source 和 event_id 去重，内容不同必须冲突告警。Outbox 是事件可靠性的实现，不代表所有跨系统更新具有即时强一致性。目录、索引和观测允许受控延迟，生产查询的可见状态和权限检查则由平台明确保障。

元数据服务维护稳定 ID、版本和状态；业务团队维护字段含义、单位及总表口径；各任务服务提供实际输入输出；Agent 团队维护 Prompt、工具与模型引用；专家确认知识。它们通过管理页面和接口合作，禁止靠开发人员日常手工直接改数据库。

## 11 与数据质量的关系

元数据服务保存质量结果引用和可用状态，质量服务执行规则。结构化校验针对数据值和契约，文档校验针对解析与定位，Agent 校验针对结果和证据，不能用一个“quality=good”替代全部规则结果。

quality_result 至少记录目标 version_id、规则及版本、处理 Run、严重性、PASS/FAIL/WARN/UNKNOWN、错误定位和确认人。元数据版本的 quality_state 只是汇总状态，发布时必须回到实际规则证据。

例如 V01 的文件 hash 正确，说明原件完整；V03 的单位和必填字段通过，说明入库契约符合；V05 的表格抽取由样本复核，说明解析可靠；V07 由专家确认，说明记忆适用条件明确。四项检查不是相互替代的。

## 12 一期如何开始开发

第一步建立元数据逻辑库、12 张示意表对应的 API 模块及身份校验。先纳管来源、表目录和文件版本，质量、权限及契约从已有设计补入，不直接把示意 SQL 当生产迁移执行。

第二步改造现有 Excel 入库脚本与填报接口，加入入库批次、原件版本、Run 和 Outbox。使用一个代表性表族走通“源文件到业务记录”的追溯，再推广其他表族。

第三步实现 NAS 受控接入与解析任务，走通“原文件到片段到索引”的关系和修订传播。完善上传状态及对账，不以路径命名代替版本管理。

第四步接入 Agent SDK 与 Langfuse 映射，查询工具写入实际证据，记忆创建与审核写入资产版本和血缘。完成撤权、来源修订、请求失败和重试验证。

一期需要能够回答：这份文件在哪里，这条实验记录来自哪次提交，这个答案用了哪些真实数据，这条经验为何可以使用，以及源数据变化会影响哪些资产。模型训练和代码自进化再扩展候选、制品、快照和发布 manifest，不阻碍基础元数据先上线。

## 13 配套 SQL 的使用边界

同目录的《RSI数据平台_元数据与血缘表结构示意_v1.0.sql》列出 12 张表的字段、主键、去重和血缘查询索引，便于研发评审。SQL 使用 MySQL 风格，不创建数据库、不含 DROP、不迁移或修改现有业务表。本次仅做设计文件，未连接任何生产数据库。

为了便于说明兼容边界，扩展和参数字段采用 LONGTEXT 保存经服务校验的 JSON 文本，后续按现网版本可改为 JSON 类型。需要参与过滤、关联或排序的核心字段使用普通列，不能把所有元数据塞进一个 JSON 字段。

引用存在性、跨团队授权、状态机、Schema 语义、质量门禁和幂等冲突由服务执行，DDL 不自动实现它们。无外键示例仍须有引用完整性校验与对账。字符集、排序规则、时间精度、索引大小、事务范围和版本兼容需要在 OceanBase 开发环境验证后，形成正式迁移脚本。

本文和 SQL 的核心结论是：元数据是一组关系表和一个应用服务模块，各业务环节负责登记，血缘由实际处理的输入输出建立。文件库、业务库、观测库和记忆库使用统一资产与版本引用互相连接。
